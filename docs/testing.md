# Testing

Run commands from the repository root. The command reference uses Windows PowerShell; CI runs the portable checks on Linux. For a short setup sequence, start with [Contributing](../CONTRIBUTING.md#quickstart-windows-powershell).

Python 3 and Node.js are needed for the quick checks. The configuration checks also need CMake. Pure C checks need a native C11 compiler; optional LVGL UI runners also need CMake, Ninja and the pinned managed LVGL sources fetched by a firmware build. The Modbus/device-network/Serial adapters require Windows and native Clang. The focused runners require the cached Debug LVGL library created by `tools/test_offline_ui.ps1`.

| Serial, saved serial logs or RTU Frames | [Serial and RTU UI](#serial-and-rtu-ui). |

Generated test binaries and captures belong under ignored `build/`. For firmware memory limits, use `ninja -C build -j 1 app` for an incremental build in an activated ESP-IDF shell; the normal repository wrapper defaults to four jobs. A clean build still belongs in pre-merge verification.

## Firmware configuration

Activate the selected SDK with its `export.ps1` or `export.sh` before configuring. Its exported `ESP_IDF_VERSION` uses major.minor (`5.4` for the pinned SDK 5.4.2). Root CMake rejects a missing or mismatched value before the SDK can regenerate `sdkconfig` with Wi-Fi Remote Kconfig sources omitted. After SDK configuration, it requires the ESP32-P4 MCU, ESP32-C6 hosted Wi-Fi target and SDIO transport. The existing compile-time checks still enforce the Tab5 SDIO pins, bus width and reset polarity.

```powershell
python tests/board_config_test.py
# If CMake is outside PATH:
python tests/board_config_test.py --cmake 'C:/path/to/cmake.exe'
```

These 20 checks execute the actual root CMake file against small SDK fixtures, including invalid exports that must leave the fixture configuration untouched. They cover both hosted-target symbol names used by the SDK 5 and 6 branches; they do not establish SDK 6 compatibility. A real pinned-SDK configure also rejected a missing export without changing the repository's generated configuration, and a subsequent configure/build with the correct export passed. The release workflow includes the portable fixture checks.

## CSV tail recovery

```powershell
python tools/test_storage_csv_tail.py --compiler 'C:/path/to/clang.exe'
```

This portable fixture compiles the actual `storage_io.c` against native files, counting stdio calls and controlling seek/read/truncate/sync/close faults. Its 32 cases check exact retained bytes, empty/missing files, LF/CRLF, binary tails, the latest complete row, 511/512/513- and 1023/1024/1025-byte boundaries, and two long unfinished rows. Recovery scans backwards using a 512-byte scratch buffer. Eight controls against the preceding source exceed the seek budgets; a 65,536-byte partial tail drops from 65,538 stdio seeks to 130 while retaining the same complete prefix. Complete files require no block reads or truncation.

Seek/read failures preserve all bytes, including a short read without a supplied errno. Truncate, sync and close failures report the first error and leave every modeled handle closed. Sync/close failures can follow a completed truncation, so those cases check the retained prefix without promising rollback or power-loss durability. Original storage checks and five existing MQTT/HTTP logging cases also pass. These checks use the host filesystem and controlled fault boundaries; physical FAT/SD timing, removal and power cuts remain in the hardware matrix.

Generated source, full storage/header/test hashes and compile/result logs stay under `build/storage-csv-tail/`. Linux CI runs the fixture and retains those files as `storage-csv-tail-logs`, including compiler/test failures. Its 32 cases are separate from the seven-suite Windows native total.

```powershell
# Inject SHA API errors and check cached description data before writing:
./tools/test_ota_image.ps1 -Modes sha-start,sha-update-first,sha-update-late,sha-finish,small-manifest
# Expire the native clock after description reads, before the first write:
./tools/test_ota_image.ps1 -Modes description-expired
```

This Windows runner needs native Clang, CMake, Ninja, Python and the pinned SDK sources, without LVGL or SDK activation. It compiles the actual updater and SDK OTA, HTTP client/parser, transport dispatch, cJSON and software SHA-256 sources. SDK source files remain unchanged; the native SHA target renames three entry points so a fixture can inject negative API returns while forwarding normal calls to the pinned implementation. Loopback HTTP serves an 8,192-byte synthetic image with an independently computed Python digest. Device partitions and boot selection are modeled in RAM; the Windows adapter preserves the P4 image header's serialized size/chip offset and verifies the real SDK application-description layout. It does not validate a physical flash image, hardware crypto faults, TLS certificates, boot or rollback.

The 52 image cases cover direct, chunked, close-delimited and fragmented transfers; empty/body/chained/fragmented redirects; hash, length and embedded-version mismatches; invalid descriptions/chip IDs; short/truncated/error responses; missing slots and begin/write/end/boot-selection faults; informational replies, complete/truncated trailers, partial/oversized headers, transport allocation/init faults, controlled SHA errors and expiry before the first write. Short and long chunked bodies with matching digests isolate the byte-count guard. Raw decimal length checks reject 64-bit/32-bit aliases before reading the description or writing the image; zero-padded matching lengths pass. Failed verification must abort before image finalization or boot selection. Direct and informational/trailer repeat cases each perform a warm-up plus 25 installs in one process, with no retained SDK allocations, transports, sockets or tasks and stable Windows handle counts. The suite records compiler/case logs, request/response hashes, the image vector and a JSON summary under `build/ota-image/`.

Three stream-bound cases supply 32 KiB over chunked/close-delimited framing against an 8 KiB manifest, including a full-body matching digest. The `9dffe34` executable reads/writes all 32 KiB before aborting. Checking the received byte count before each SDK perform call stops the new path after the first excess 1 KiB buffer: 9 KiB read/written, one abort, no finalization/boot selection and all resources released. The SDK may write the current read buffer before the updater observes the excess count.

Four SHA cases inject one negative API return at initialization, the first or a later update, and digest completion. With `6d6a42a` production code, first/later update errors still write all 8 KiB before aborting. The new check runs before each SDK perform call: the first-update error prevents partition writes, while a later error stops at 2 KiB, including the current SDK buffer. A chunked image with a 512-byte manifest also stops before partition writes because cached description data already exceeds the limit; the previous code writes 1 KiB. Initialization failure makes no request, and digest-completion failure never finalizes/selects the image. Every case releases all resources. These tests verify controlled API-error handling; they do not reproduce failures of the P4 SHA accelerator.

The actual image guard shares a cooperative five-minute deadline across connection, redirects and download, with checks around SDK download/write operations and before finalization. Three byte-trickle cases exercise header, description and body phases with a 20x host-only monotonic clock; the production timeout constant stays five minutes. They finish after 300-304 virtual seconds (about 15 wall-clock seconds), release all resources and never finalize/select a boot partition; body timeout aborts an active RAM write. JSON records both elapsed values and the scale. Prior-executable probes reproduce image informational rejection, partial-header/trailer resource-check failures, oversized-header acceptance and image reads after aliased length declarations.

The `description-expired` case advances only the native clock by 300,000,000 microseconds after 1 KiB of description data is hashed normally. The `a9788d7` executable begins a partition write and writes that 1 KiB before its timeout check. Checking time before each SDK perform call now rejects the same response with zero partition starts/writes, no finalization/boot selection and all resources released. JSON retains the clock advance and hashed byte count. This is a controlled deadline boundary, separate from the byte-trickle timing tests; it does not measure physical scheduling or flash latency.

The previous updater rejected a valid image after a 266-byte redirect body: the actual SDK drains that body through data events without emitting a redirect event. Hashing only HTTP 200 image bytes fixes this case. Four private mutations removing the response-status filter, digest comparison, byte-count guard or version comparison are rejected by the real SDK fixture. The shared HTTP adapter still passes all 79 console cases.

The same runner includes 27 manifest fetches through the real SDK HTTP client/cJSON and shared guarded HTTP transport/resolver. The original framing cases cover direct, fragmented, chunked, close-delimited, large/chained redirects, incomplete fixed-length/chunk streams, JSON/NUL/size/status failures and 64-bit length boundaries. Before the framing fix, the client returned success for a 284-byte JSON body declared as 304 bytes or sent without a final chunk, and 2,166-byte redirect bodies overflowed the final manifest buffer. The fetcher checks completion before parsing, resets each request and only copies HTTP 200 data. Independent framing checks remain effective when the SDK length becomes negative. The guarded header parser rejects the maximum 64-bit length; real EOF completes valid close-delimited responses. Four earlier private controls rejected removal of completion/header checks or both redirect protections.

New cases cover informational replies, complete/truncated trailers, partial/oversized headers, transport allocation/init failures, silent header/body waits and headers trickled one byte at a time. The actual guard bounds metadata at 8 KiB and shares one cooperative 15-second deadline across the request and redirects. The three wait/trickle cases end around 15 seconds, with no retained resources. A direct fetch and an informational/trailer fetch each repeat 25 times after warm-up with stable handles. Fetch cases never reach image or boot APIs. Prior-executable probes reproduce resource-check failures for partial headers/trailers and rejection of the final manifest after a separated informational reply; the guarded path passes them. All 79 HTTP Console cases pass after the shared transport gained response reset for redirects.

CI runs this suite seventh and retains its evidence. A separate checkout passes all 79 cases using only the extracted hosted source bundle; all 79 also pass in hosted CI. A seven-suite orchestration control stubs the preceding six suites, checks their order/arguments and runs the actual SDK suite. Earlier missing SHA/OTA header controls fail before compilation or archive creation, retain the final-suite error and restore the temporary environment.

## MQTT lifecycle and storage

The [release workflow](../.github/workflows/release.yml) defines a `native-ui` job on `windows-2025`, after the Linux firmware build.
