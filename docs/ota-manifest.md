# OTA manifest contract

Stable OTA checks `tab5_os.json` from the latest non-prerelease GitHub release. The bounded schema is:

```json
{
  "schema": 1,
  "version": "v0.6.0-01234567",
  "hardware": "m5stack-tab5",
  "size": 2087008,
  "sha256": "64 lowercase hexadecimal characters",
  "url": "https://github.com/DevanMetz/Tab5OS/releases/download/v0.6.0/tab5_os.bin",
  "channel": "stable",
  "minimum_predecessor": "v0.5.1"
}
```

The updater accepts only schema 1, `m5stack-tab5`, the stable channel, a newer semantic version, a compatible minimum predecessor, an image no larger than the 6 MiB OTA slot, and the repository's immutable tagged-release URL prefix. It caps the HTTP 200 JSON body at 1536 bytes and validates the entire received byte count. Redirect bodies cannot consume this limit. Fixed-length and chunked bodies must complete before parsing; a successful SDK request alone does not establish completion. Framing headers are recognized without relying on the SDK's signed length value, including very large declared lengths. Valid close-delimited responses remain supported. Schema 1 requires exactly the eight fields above; duplicate or extra members, arrays and nested objects are rejected. Nesting is rejected before cJSON recursion. Raw NUL/control bytes, escaped U+0000 and non-JSON whitespace cannot truncate or disguise values. Ordinary JSON whitespace, escaped ASCII and literal backslashes remain supported.

Manifest requests and image downloads use the shared guarded HTTP transport with cooperative total budgets of 15 seconds and five minutes respectively. These budgets cover DNS, connection, redirects, headers and body; the image path also checks time before and after each SDK download/write call and before finalization. The first check prevents a known expired deadline from starting a write of cached description data. The guard bounds response metadata at 8 KiB, waits past informational replies, validates and discards chunked trailers, and withholds unfinished headers from the SDK to avoid its partial-value cleanup leaks. Redirects reset framing for each response, including on a reused connection. Image reads select the FIN signal needed by the SDK streaming API to complete close-delimited responses. Cleanup releases the injected transport after the SDK client. Physical Wi-Fi/TLS/flash latency remains a hardware check.

Before reading the image description, Tab5 OS checks the raw Content-Length when supplied against the manifest size, without the SDK OTA API's narrowing to `int`. Oversized declarations cannot alias a valid image size; leading decimal zeroes remain valid. Before changing the boot partition, it verifies the exact downloaded byte count, complete HTTP framing, SHA-256 of the complete published `.bin`, and the version embedded in the ESP-IDF application description. Only HTTP 200 image data enters the hash/count: the SDK drains redirect bodies without emitting a redirect event. Any mismatch aborts the OTA handle and leaves the running boot partition selected. A verified image still remains pending until the existing 30-second display/storage/NVS health window passes.

Before each SDK download/write call, the updater rejects a recorded SHA-256 failure or a received byte count above the manifest size. This also checks data cached while reading the image description before the first partition write. During later downloads, the SDK may have written the current buffer before the updater observes the failure or excess count; the image is aborted before finalization or boot selection.

Tag builds publish `tab5_os.bin`, `tab5_os.json`, and `SHA256SUMS` from the same CI build. Tags containing `-` are GitHub prereleases with channel `beta`, so the stable updater does not consume them through GitHub's latest-release endpoint.

## Native validation

Run `./tools/test_ota_manifest.ps1` with native Clang and the pinned ESP-IDF 5.4.2 sources; use `-Compiler` and `-IdfPath` when needed. The runner compiles the actual `ota_manifest.c` and SDK cJSON with strict warnings. Its 379 checks exercise every valid-response fragment size, the exact 1536-byte cap, redirects, request/init/transport errors, deadline and metadata failure mapping, incomplete framing/status precedence, malformed or ambiguous metadata, 32-bit size bounds, cJSON allocation failures/recovery and version/slot/URL gates. Invalid parsed results are cleared, and every request releases its client, injected transport and JSON allocations. Four earlier private mutations of the bounds, member count, size and output cleanup are rejected.

The native CI job runs these checks using cJSON source/header/license files in its pinned artifact. Controlled HTTP events and transport results provide the response; all image/hash APIs in this fixture fail closed if called. The [hosted run for `a9788d7`](https://github.com/DevanMetz/Tab5OS/actions/runs/37745766579) passes all 379 parser checks, the preceding 51 image cases and all 27 SDK manifest fetches alongside the existing native suites: 814 checks total. Downloaded artifacts verify the results, three real-time manifest deadlines, three accelerated image deadlines, controlled SHA API failures, stable resources and all 51 SDK input hashes.

Run `./tools/test_ota_image.ps1` separately on Windows with Clang, CMake, Ninja and Python. Its 79 cases compile the actual updater and SDK OTA/HTTP/parser/transport/cJSON/software SHA-256 sources against loopback HTTP and RAM partitions. Both operations run the actual shared transport/resolver with the deterministic platform DNS adapter. The 52 image cases verify redirected and fragmented transfers, exact digest/length/version gates, malformed/truncated images, slot/write/finalization/boot-selection faults, guarded metadata, transport allocation faults, controlled SHA API errors, expiry before the first write and cleanup over a warm-up plus 25 installs. Matching-digest short/long bodies isolate the length check. Four earlier image guard mutations are rejected, and the actual SDK image redirect regression is reproduced before the fix.

Three oversized-stream cases serve 32 KiB against an 8 KiB manifest over chunked or close-delimited framing, including a digest matching the full oversized body. The `9dffe34` executable reads/writes all 32 KiB before its final size check. The streaming guard stops all three at 9 KiB with the configured 1 KiB reader, aborts the RAM image and releases every tracked resource without finalization/boot selection.

Four SHA cases inject negative API returns at initialization, the first or a later update, and digest completion. The native target renames three entry points when compiling the unchanged SDK SHA source; normal calls forward to its pinned implementation. These are controlled API errors, not reproduced hardware crypto failures. Against `6d6a42a`, update errors still permit all 8 KiB to be written. The new check stops a first-update error before partition writes and a later error after 2 KiB, including the current SDK buffer. A fifth case supplies a chunked image against a 512-byte manifest: description data already exceeds the limit, so the new check prevents the previous 1 KiB cached write. Initialization and digest-completion errors also release resources without finalization or boot selection.

The `description-expired` case advances the native clock by five minutes after 1 KiB of description data has been hashed normally. The `a9788d7` executable still starts a partition write and stores that cached 1 KiB before returning timeout. The check before each SDK perform call now returns timeout with zero partition starts/writes, no finalization/boot selection and all resources released. JSON evidence records the controlled clock advance and hashed byte count. This verifies application behavior at a known expired deadline; physical scheduling and flash latency remain unmeasured.

Image probes of the preceding executable reproduce false rejection after informational replies, resource-check failures after complete trailers or partial headers, acceptance of oversized headers, and image reads after aliased large Content-Length declarations. The guarded image path passes these cases and rejects mismatched lengths before description reads or partition writes. Direct and informational/trailer installs each repeat 26 times with stable resources. Three image trickle cases cover headers, description reads and body writes, using a 20x host-only monotonic clock to exercise the unchanged five-minute production constant in about 15 wall-clock seconds. They return timeout with released resources and no finalization/boot selection; an active RAM write is aborted. Their JSON evidence records virtual elapsed time, wall time and clock scale.

Twenty-seven real SDK manifest-fetch cases cover fragmented/chunked/close-delimited bodies, large/chained redirects, exact/over-limit responses, malformed JSON/NULs, HTTP errors, incomplete framing, 64-bit length boundaries, informational replies, complete/truncated trailers, partial/oversized headers, transport allocation faults and stalled/trickled requests. Direct and informational/trailer fetches each repeat 25 times after warm-up with stable resources. Silent header/body waits and a byte trickle end around 15 seconds with all resources released; the trickle keeps each individual read active and tests the total budget.

Before the earlier framing fix, the SDK accepted 284 JSON bytes against a declared 304-byte response or unfinished chunk stream, and 2,166-byte redirect bodies rejected a valid final manifest. Four earlier private controls rejected removal of completion/header checks or both redirect protections. Separate probes of the preceding updater reproduce resource-check failures for partial headers/trailers and rejection of a valid final response after an informational reply. The new guarded path passes all three. Its real EOF handling completes valid close-delimited responses. A separate checkout passes all 79 cases using the hosted source-only bundle; the preceding 78 cases also pass in hosted CI. All 79 HTTP Console cases pass with the streaming EOF option disabled for that client.

Device image-header types are adapted to preserve the P4 serialized layout under the Windows ABI; the real SDK application-description layout is checked. Image finalization and boot selection are simulated in RAM. Physical flash-image validation, hardware SHA failures, boot, rollback, TLS and both panels remain in the [hardware checklist](hardware-smoke-checklist.md). Hosted execution of the new expiry-before-write case remains to be verified.

## Trust boundary

This contract prevents truncation, substitution after manifest retrieval, accidental cross-hardware installs, and unstructured `latest` downloads. It does not yet provide an independent release signature: GitHub account/repository control and Web PKI remain trusted. Phase 4 still requires signed manifests or images with an embedded public verification key before v1.0. Secure boot, flash encryption, and irreversible eFuses remain a separate opt-in hardened-device profile.
