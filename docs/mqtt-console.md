# MQTT Console lifecycle

Connect explicitly to a broker using `mqtts://` or `wss://` for certificate-bundle verification. Plain `mqtt://` and `ws://` require a second CONNECT tap within five seconds with unchanged connection settings. The default public test broker and device-specific topic are observable; use a disposable test message. SUBSCRIBE accepts one ASCII topic filter, and PUBLISH accepts one ASCII topic without wildcards. Topics/filters contain 1-127 bytes. QoS and retained-message controls apply to subsequent actions.

An explicit TLS/WSS profile stores the broker URI, username, password and topic in device settings. Developer builds do not encrypt these settings. Cleartext profiles stay in memory; deleting a saved profile requires two taps within five seconds. See the [profile and metadata formats](data-formats.md).

## Broker settings and connection results

Broker URI input is limited to 255 bytes, including outside spaces/tabs. The raw limit is checked before trimming, so padding cannot hide a clipped endpoint. The pinned SDK URI parser checks host/port syntax; an explicit port must be 1-65535, and bracketed IPv6 hosts must pass address parsing. Scoped IPv6 URI literals are not supported. Embedded credentials and URI fragments are rejected. MQTT/MQTTS accepts a host and optional port/root slash; WS/WSS also accepts a path and query, passed unchanged to the SDK. The four scheme names are matched without regard to case.

Username and password each accept up to 64 UTF-8 bytes, both for Connect and Save Profile. The first excess character remains in the field and the raw byte count is checked before starting or saving. For example, 16 four-byte characters fit; 17 do not. A saved profile retains the accepted credential exactly. The URI field likewise retains a 256th ASCII byte so an overlong endpoint cannot silently connect to its prefix.

Editing the broker URI, username or password cancels a pending cleartext confirmation, including edits that restore the original text. The next CONNECT tap must show the warning again; a second tap within five seconds confirms the current settings. Focusing an input also cancels an earlier confirmation.

Re-opening the app reloads a valid saved TLS/WSS profile with its password masked. Connect stays explicit, and logging and retain default off. An invalid profile or a settings read error leaves the default form and reports the problem. DELETE PROFILE remains available when a key exists or its presence cannot be determined; confirmed absence disables it. You can explicitly replace an invalid profile by saving valid settings.

If saving or deleting reports **not confirmed**, the operation may already have changed device settings. The current form remains available; re-open to check what can be read, or use two fresh DELETE PROFILE taps to remove the key. Save, Connect/Disconnect, Clear, connection-field edits, form focus and expiry dismiss an earlier delete confirmation. DELETE PROFILE dismisses a pending cleartext connection confirmation, so the next Connect tap shows its warning again.

The connected status uses the accepted transport, even if the draft is later changed. MQTT/WS reports **confirmed cleartext**; MQTTS/WSS uses certificate verification. A transport/connection error immediately disables new Subscribe/Publish actions while the session remains owned until Disconnect/Home cleanup. The error survives the SDK's subsequent disconnect and ordinary acknowledgment statuses. Storage failures or omitted metadata/history warnings appear alongside it. Clear dismisses pending connection/profile-delete confirmation and clears history while retaining a connection error. Disconnect and a fresh connection reset the old error. A rejected subscription acknowledgment reports **Broker rejected subscription**, leaving the live connection usable.

Transport failures display every supplied nonzero ESP error, signed TLS stack code, certificate verification bitmask and socket errno. ESP error names include their hexadecimal code; TLS codes retain their sign, and verification flags use hexadecimal. Socket descriptions are bounded. A zero ESP error is omitted, so a socket failure is never described as `ESP_OK`. If all four fields are zero, the status says **SDK supplied no error details**. These codes report the SDK's diagnosis; an empty report does not identify a cause.

## Subscribe and Publish

Each accepted tap captures its topic/filter, payload, QoS and retained state. The existing worker calls the SDK with that captured data, so editing the form or toggling QoS/retain while it waits affects the next action. The status and TX preview identify the captured topic. Subscribe and Publish remain unavailable while an action is pending or executing; their callbacks also reject stale disabled taps.

The SDK's Subscribe call writes to the network, and its Publish enqueue call takes a lock shared with the SDK network task. Both run on the worker so a network wait can finish while the UI remains responsive. The same worker processes Disconnect cleanup after releasing any action, and selects pending work and cleanup under one lock to preserve client ownership when notifications arrive together. Work still waiting for dispatch is discarded if the worker observes that stopping has begun. An action already inside the SDK can finish accepting a publish after Home; the old session's opted-in TX metadata then records that acceptance before cleanup ends.

Publish accepts an empty payload or up to 512 UTF-8 bytes. Excess input stays visible and is rejected before an action is queued. For example, 128 four-byte characters fit; 129 do not. A 128-byte ASCII topic is also retained and rejected instead of publishing to its 127-byte prefix. QoS 0 uses the SDK's explicit outbox storage option, so its successful message ID of zero is accepted. If the bounded outbox is full, the status asks you to wait before retrying. Queue acceptance is the TX outcome; broker delivery is established separately by the MQTT exchange.

A broker acknowledgment can arrive after the SDK releases its API lock but before that API returns to the worker. Action completion preserves any newer acknowledgment, subscription rejection, receive or disconnect status instead of replacing it with a queue/request message. An event revision is compared under the existing app lock; this does not delay the SDK callback or require another task.

## Prepare a byte payload

In Byte Lab, prepare the Hex or encoded Number value and tap **Copy bytes**. In MQTT, **PASTE BYTES** captures those complete 0-128 bytes into a separate RAM draft and selects **PAYLOAD: BYTES**. Review the Hex view, topic, QoS and retain choice, then tap **PUBLISH**. Paste and changing payload mode never send, subscribe or write metadata. An empty byte payload is valid.

The payload button switches between the prepared bytes and **PAYLOAD: TEXT**, preserving the text field within the open screen. Text still accepts up to 512 UTF-8 bytes; its excess input remains visible and is rejected only when Text is the selected publish body. The bytes are prepared in Byte Lab rather than edited in MQTT. Their preview shows every original byte, including NUL and non-ASCII values.

Changing or clearing the shared clipboard does not replace an already prepared byte draft. Publishing captures the selected body's bytes and original topic/QoS/retain before dispatch; subsequent paste, mode or field edits cannot change that queued action. Prepared bytes and the selected mode survive Disconnect/Home in RAM, and the visible mode identifies which body the next explicit Publish uses. Clear clears history and the saved receive while preserving the prepared transmit draft. Restart clears prepared bytes. They are never stored in the connection profile or SD metadata.

Paste and mode switching dismiss pending cleartext/profile-delete confirmation without replacing connection or storage errors. They remain available offline or while an action waits, and are disabled throughout cleanup; stale clicks also revalidate that ownership. Byte publishes use the SDK's explicit byte length. Only after enqueue copies the bytes into its outbox does history convert them to a labeled ASCII preview.

## Received messages and previews

The pinned SDK supplies the topic only on the first receive event. A header can fill its input buffer, leaving that event with zero payload bytes; the next event then also has offset zero and no topic. MQTT retains the original topic, timestamp, QoS, retain flag, message ID and total byte count while assembling contiguous data-only continuations. An empty payload completes on its topic-bearing event. History and metadata receive one entry only when the declared payload is complete.

Negative lengths/offsets, missing bytes or topic, inconsistent message fields, gaps, overlaps and repeated final fragments are rejected. A rejected continuation clears the assembly; it cannot finish later using stale bytes. Connection/error events also clear partial assembly. A fresh topic-bearing message can replace an unfinished one. A valid final fragment arriving before SDK shutdown finishes can still enter the old session's captured log queue after Home; unfinished messages produce no row.

Received payloads use a 512-byte ASCII preview. Printable ASCII, line feeds and tabs remain visible; carriage returns become line feeds and other bytes become `.`. The byte count describes the full received payload, including binary or larger messages. The RX history explicitly labels this representation as an ASCII preview and marks a capped payload.

Received topics use a 127-byte printable ASCII view. Longer topics are shortened, and non-printable/non-ASCII topic bytes become `.`. A changed topic is explicitly labeled **topic preview** in status/history, and its metadata outcome is `preview_truncated`, even when its payload fits. Such a topic field is a bounded representation and must not be treated as the complete original broker name. Topic controls/line breaks cannot create extra metadata lines. Ordinary printable ASCII names, including quotes, retain their normal CSV quoting.

## Copy raw receive bytes

**COPY RX** shares the latest complete 0-128-byte receive with the RAM byte clipboard. Open Byte Lab and tap **Paste hex** to inspect exact binary bytes. Copy does not subscribe, publish, reconnect or write an SD row. The saved source label shows its captured topic, full byte count, QoS and retained flag; changing the draft topic or publishing leaves that receive intact. A shortened/transformed topic remains labeled **topic preview**, while the copied payload is exact.

An incomplete or rejected assembly cannot replace the last complete receive. A newer complete payload over 128 bytes disables copying and preserves the existing clipboard; it cannot be copied as a shortened prefix. An empty payload is a valid zero-byte copy. History-ring overflow does not lose the latest complete receive.

Disconnect/Home retains the receive in RAM independently of SDK buffers. Copy stays disabled while cleanup is busy, including during final fragments and error reporting; it is available after cleanup or re-entry. Starting a new session resets the saved receive. **CLEAR** clears the saved receive and queued/visible history, preserves accepted metadata and leaves the shared clipboard unchanged. Copy dismisses pending Connect/profile-delete confirmation, and its feedback does not replace connection or storage errors. The saved receive and clipboard disappear on restart.

## Disconnect and Home

DISCONNECT posts the SDK's disconnect request and hands the session to the cleanup worker. Home also deletes the UI timer, clears the visible password, and detaches the widgets immediately. The worker completes any in-flight storage call, waits for SDK stop/destroy, writes already accepted pending metadata, and releases the session's buffers. MQTT remains busy throughout this work, including file close and storage-error reporting, so the existing OTA restart blocker cannot treat an unfinished cleanup as idle.

Re-opening MQTT while cleanup is running shows STOPPING. Connect, Subscribe, Publish, profile actions and the log toggle cannot start work during shutdown; their callbacks also check this state when an old click arrives. Connect, Save/Delete Profile and the log toggle still reject a disabled click after cleanup finishes but before the UI timer restores the controls. Delayed SDK connection/acknowledgment/error events cannot re-enable Subscribe or Publish or overwrite the shutdown status. A final received message can still join the bounded ring before SDK shutdown completes. The worker publishes its final status together with the idle state, preventing old cleanup from overwriting a new session's status.

Connect recreates required buffers if cleanup finished before the UI timer refreshed them. It also clears the previous session's pending status before starting a new client, so an older completion cannot replace the new connection status.

The preallocated worker remains asleep between actions and sessions. SDK action calls, shutdown and filesystem calls are cooperative operations; their configured network timeouts do not establish a strict whole-cleanup wall-clock bound. Home can detach the screen while the worker remains busy.

## Pending SD metadata

SD logging starts OFF whenever MQTT opens and must be enabled explicitly. It records timestamp, TX/RX, topic, QoS, retained state, payload byte count and outcome. It never records credentials or payload contents. The log choice is sampled when a receive message completes or the SDK accepts a publish. Turning logging off stops future capture; metadata already accepted remains queued for writing.

The metadata queue holds eight pending entries plus one in-flight write and contains no payload preview. It is independent of the eight-entry UI message ring: history drops do not remove accepted metadata. If storage falls behind and its queue overflows, the oldest pending entries are dropped. The status reports omitted metadata while connected and again after Disconnect; the count persists until a new session. Both queues share one bounded PSRAM allocation.

The existing worker performs every filesystem operation, including directory creation, tail repair, append, flush, durable sync and close. The UI timer only updates history and controls. A pending Subscribe/Publish or shutdown takes precedence over the next queued write, although an in-flight filesystem call must return first. Clear affects visible history while accepted metadata remains owned by the worker.

Cleanup captures the old session's log choice before Home resets the new screen, allowing final SDK events to retain that choice through shutdown. It writes accepted entries serially and stops at the first storage failure. Each entry must complete flush, durable sync and close before it counts as successfully saved. A sync or close failure may leave bytes behind; the status therefore says the metadata log was **not confirmed saved**. Failure disables logging and discards remaining queued metadata for that session. Disconnect and start a new session before enabling logging again.

The captured storage-error callback runs once for the session's first error, on the worker after file close, while MQTT is still busy. During shutdown it runs after buffers are freed; during an active session it can run while the buffers remain allocated. Home can detach and re-enter while that callback waits. The callback must be thread-safe and must not call LVGL.
